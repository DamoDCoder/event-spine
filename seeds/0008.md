A single flipped bit in a record's **offset field** was accepted, and the reader
returned offset 536870912 from a log holding `[0, 5)`.

The offset field was deliberately outside the CRC's coverage. `record.go` said
why: the offset is redundant with the reader's position in the sequence, so a
flipped offset is caught by comparing against the offset the reader expected —
which is what `DecodeAt` did at every call site.

Compaction removed that guarantee and nothing noticed. Once records can be
missing, a scan cannot name the offset it expects next, so the gap-tolerant read
path checks `offset >= atLeast` instead of `offset == want`. A flip that lands
*above* the expected offset passes. The comment on `readRecordFrom` even says
so — the case it names as unseeable is this one, written down and then left
alone.

The consequence is worse than one bad read. A segment scanned during recovery
takes its `next` from the last record it saw, so one flipped high bit moves the
log's tail to 4611686018427387911 and every subsequent append is assigned an
offset from there.

Minimized to three workload steps and one flipped bit.
