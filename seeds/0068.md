**No fault at all.** Twenty-two ordinary steps in `os` mode, and `Sync` returns
`sync 00000000000000000000.log: file is closed`.

It is the fix for the power-cut hole, one move later. `Sync` now owes a flush to
every segment a roll sealed without syncing, so the log keeps a list of them.
Compaction closes a sealed segment when it swaps in the compacted replacement —
and nothing removed the closed handle from that list, so the next `Sync` tried
to fsync a file that no longer exists.

The compacted segment's data is durable by then: compaction writes the
survivors to a temporary file, syncs it, renames it into place, and syncs the
directory. So the right answer is for the log to forget the old handle rather
than to sync it, and the records compaction dropped were superseded ones it is
entitled to drop.

The interesting part is why this took until now to appear. The simulation
workload ran only in `batch` mode for two milestones, where a roll syncs the
outgoing segment and the list is always empty. Adding the durability mode to the
sweep found this on the first run of 200 seeds, in six of them, with no fault
injected at all.

Re-recorded on 2026-08-14: rolling now syncs the outgoing segment in every mode,
which added an operation to this run. The list of syncs owed that this seed was
committed for no longer exists — the invariant it was tracking is enforced at
the roll instead — so the seed guards the area rather than the mechanism.
